# Система секций

Справочник по тому, что сейчас реально в коде: `types/site.ts`,
`components/SectionRenderer.tsx`, `components/sections/*`,
`content/site.config.ts`. Если код и этот файл разойдутся — верить коду,
и поправить этот файл.

Каждая секция — папка одного и того же устройства: `index.tsx` (роутер
по `variant`), `variants/` (файл на дизайн), `parts/` (общие куски).
Как добавить новый вариант — раздел 7.

Общее для всех секций: базовые поля приходят из `SectionBase`
(`types/site.ts:9`) — `id` (обязательное, anchor + key), `surface?`,
`number?`, `eyebrow?`, `title?`, `lead?`, `nav?`. Но **не все компоненты
реально читают все поля SectionBase** — расхождения отмечены в таблице
ниже, они не баг, а осознанная форма конкретной секции.

`nav?` вообще не читается компонентом секции — его использует
`lib/seo.ts:107` (`buildNav`), чтобы собрать пункты меню хедера из тех
секций, где `nav` задан. Это единственное поле, которое живёт на уровне
страницы, а не конкретного компонента.

**Важно про колонку «По умолчанию» в таблицах ниже.** Для `variant`
(и для `Stats.containerVariant` / `Contact.layout`) там написано
значение тарифа **«Эконом»**. Умолчание не зашито в компонент: если
`variant` не задан в `site.config.ts`, его подставляет
`components/SectionRenderer.tsx` из таблицы `lib/preset.ts` по текущему
`theme.preset` — в «Стандарте» это будут карточные раскладки. Значение,
явно указанное в конфиге, всегда главнее. Подробно — `docs/presets.md`.

## 1. Секции и их props

### Hero — `components/sections/Hero/`, тип `"hero"`

Шесть вариантов, роутер `index.tsx` выбирает не только по `props.variant`
напрямую: пара `type-only` ↔ `split` разрешается через
`resolveHeroLayout` (`resolved`), потому что `widget` сам включает
`split`, а `split` без `image`/`widget` падает обратно на `type-only`.
Для остальных четырёх вариантов `resolved === props.variant`. Роутер
также проверяет несовместимые комбинации полей и в dev-режиме пишет
`console.warn` (без падения, секция просто рендерится как есть) —
таблица предупреждений ниже.

| Поле | Обязательное | По умолчанию | Примечание |
|---|---|---|---|
| `headline: string[]` | да | — | строки заголовка, переносы вручную |
| `id` | да | — | |
| `surface` | нет | `"paper"` | `centered` держит `"ink"` по умолчанию |
| `variant` | нет | `"type-only"` | см. таблицу вариантов ниже |
| `rail?` | нет | — | вертикальный колонтитул на левом поле. Читают только `type-only`/`split`/`centered` — `showcase`/`billboard`/`search` рельса не рендерят вовсе (в них нет левого поля) |
| `lead?` | нет | — | |
| `actions?: CtaLink[]` | нет | `[]` | не читает `search` (там вместо кнопок поле) |
| `facts?: HeroFact[]` | нет | `[]` | блок «шапка дела», 3 факта в ряд |
| `image?` | нет | — | локальный путь `/images/...`, см. раздел 2. Занимает вторую колонку/панель в `split`, `showcase`, `billboard`, `search` |
| `widget?: HeroWidget` | нет | — | карточка метрик во второй колонке. **Сама включает раскладку `split`**, `variant` для этого задавать не нужно. Работает также в `showcase` (в панели вместо фото); в `billboard`/`search` не рендерится — они умеют показать только фото (`IMAGE_ONLY`, dev-предупреждение) |
| — | — | — | `image` и `widget` делят одну колонку/панель: если заданы оба — показывается фото, виджет пропускается (в dev — `console.warn`) |
| `badge?` | нет | — | плашка-анонс над заголовком («Версия 2.0»). Читает только `showcase` и `search` — в остальных раскладках это место занимает рельс/колонтитул |
| `frame?: "plain" \| "browser"` | нет | `"plain"` | оправа медиа-панели `showcase`. `browser` рисует поверх фото полосу окна (3 точки) — витрина интерфейса, а не фотография. Без `image` не используется |
| `proof?: HeroProof` (`avatars?: string[]`, `text`) | нет | — | строка доверия под кнопками: до 4 аватаров внахлёст + фраза. Читает только `showcase` |
| `search?: HeroSearch` (`label`, `placeholder?`, `submitLabel`, `action`, `name?`) | нет | — | настоящая форма `method="get"`, уходит на `action` без JS. Читает только `search`, обязательна для этого варианта (без неё пусто там, где должно быть главное действие) |
| `trust?: HeroTrust` (`text`, `items: { label, icon? }[]`) | нет | — | строка «нам доверяют»: имена текстом + иконка из `lib/icons.ts`, не логотипы-картинки. Читает только `search` |
| `overlay?: HeroOverlay` (`rating?` 0–5, `quote`, `author`, `role?`) | нет | — | отзыв поверх фото (`md:absolute` внутри бокса медиа, на мобильном — обычным блоком под фото). Читает только `search`, требует `image` |
| `number`, `eyebrow`, `title`, `nav` (из SectionBase) | — | — | **не используются Hero** — заголовок берётся только из `headline` |

**Варианты (`variant`):**

| Значение | Раскладка | Требует |
|---|---|---|
| `type-only` | голая типографика, рельс на левом поле | — |
| `split` | текст слева, фото/виджет справа, рельс на поле (1/6/5); потолок `--size-h1` понижен до 72px | `image` **или** `widget` (иначе откат на `type-only`) |
| `centered` | центрированная афиша на тёмной земле (`surface="ink"` по умолчанию), без второй колонки | — (`image`/`widget` не рендерятся, dev-предупреждение) |
| `showcase` | витрина продукта 6/6: `badge` над заголовком, медиа в поднятой панели (`Card variant="elevated"`) справа, `proof` под кнопками; рельса нет | `image` или `widget` (иначе половина экрана пуста, dev-предупреждение) |
| `billboard` | афиша во всю ширину окна: акцентная панель с текстом слева (без `Container`), фото встык к краю справа, свой компактный `<h1>` без акцентной последней строки | `image` обязателен (только фото, не `widget`) |
| `search` | сервисный первый экран 7/5: поисковая строка вместо кнопок, `trust` под ней, фото с `overlay`-отзывом справа | `image` обязателен (только фото, не `widget`) |

Все пять новых вариантов (`centered`, `showcase`, `billboard`, `search`
плюс сопутствующие типы) добавлены по алгоритму раздела 7 — новый файл
в `variants/`, новое значение в `HeroSection["variant"]`, строка в
`VariantMap` роутера. Общие куски (`HeroPanel`, `HeroProof`,
`HeroSearch`, `HeroTrust`, `HeroOverlay`, `headlineScale.ts` с
`COMPACT_H1`) лежат в `Hero/parts/` — они переиспользуются несколькими
вариантами, а не продублированы в каждом.

### Stats — `Stats/`, тип `"stats"`

Девять вариантов. `band`/`grid` — исходные плоские раскладки без заголовка
секции (`eyebrow`/`title`/`lead` из SectionBase не читают вообще, только
`number`). Остальные семь — карточные, и у них есть чему показать
заголовок, поэтому они его читают через общий `parts/StatsHeader.tsx`.

| Поле | Обязательное | По умолчанию | Примечание |
|---|---|---|---|
| `items: StatItem[]` (`value`, `label`, `suffix?`, `icon?`, `text?`) | да | — | `icon`/`text` — опциональные, читают только карточные варианты (см. таблицу ниже); без них соответствующий кусок карточки просто не рендерится |
| `surface` | нет | `"paper"` (у `dark` — `"ink"`) | |
| `variant` | нет | `"band"` | см. таблицу вариантов |
| `containerVariant: "flat" \| "elevated" \| "bordered"` | нет | `"flat"` | подложка под цифрами. Читают **только** `band`/`grid` — карточные варианты сами решают оправу каждой карточки через `Card`. `flat` — линейки сверху и снизу секции, блока нет. `elevated` — `rounded-card bg-card shadow-md`, `bordered` — `rounded-card border-accent-border bg-card`. У обоих непустых вариантов линейки секции снимаются (`ruleTop` и `border-b`): сквозная линейка во всю ширину перечёркивала бы блок |
| `image?` | нет | — | фото для `variant="photo"`. Без него эта раскладка не рендерится вовсе (роутер в dev — `console.warn`) |
| `number`, `eyebrow`, `title`, `lead` | нет | — | читают только карточные варианты (см. ниже); `band`/`grid` — только `number` |

**Варианты (`variant`):**

| Значение | Раскладка | `icon`/`text` |
|---|---|---|
| `band` | плотная полоса 2/4 колонки с разделителями, ячейка центрирована (`StatItems align="center"`) | не читает |
| `grid` | свободная сетка `sm:2 lg:4` без разделителей, всё по левому краю | не читает |
| `badge` | эйброу пилюлей (`Badge variant="soft"`) + крупный заголовок + лид по центру; карточки с круглой плашкой под иконкой | `icon` — плашка; `text` — абзац под подписью |
| `playful` | то же, что `badge`, но без пилюли эйброу (`eyebrowStyle="plain"`) — легче по тону. Раскраска плашек по цвету item из референса не переносится: в шаблоне один акцент на страницу (см. правило «6 мест», `docs/presets.md`), а не палитра на карточку | `icon`, `text` |
| `plain` | заголовок по центру без пилюли, иконка без плашки — просто акцентный штрих над числом | `icon`, `text` |
| `dark` | то же, что `plain`, только `surface="ink"` по умолчанию — карточки сами подхватывают тёмную поверхность через `--card-bg`, собственных цветов в варианте нет | `icon`, `text` |
| `rows` | заголовок слева (`align="left"`), плоские колонки на верхней линейке: иконка + подпись сверху, фраза «`value` + `suffix`» одной строкой (`suffix` тут пишут с пробелом впереди — это слово после числа, «` Years`», а не хвост вроде «%»), описание снизу | `icon` — у подписи; `text` — описание (без него колонка короче) |
| `bento` | заголовок пилюлей по центру, двухколоночная сетка: первая карточка — акцентная рамка (`bordered-accent`), последняя — на `data-surface="ink"`, остальные — `framed`. Асимметрию ширин колонок в референсе (2×2 bento с разными пропорциями по рядам) не повторяет — это отдельная задача на произвольные col-span/row-span (см. нишу «Бизнес — SaaS», `docs/section-system.md`, раздел 6), а не смену токенов; здесь двухколоночный поток, устойчивый к любому числу items | `icon`; `text` — если задан, заменяет `label` (иначе показана `label`) |
| `photo` | фото с заголовком/лидом поверх (тёмный градиент снизу) слева, сетка карточек справа | `icon` |

### Features — `Features/`, тип `"features"`

Пять вариантов. `table`/`cards` — исходные, заголовок берут из обычного
`SectionHeader`. `cards-cta` и `bento` центрируют заголовок пилюлей
через свой `parts/FeaturesHeader.tsx` (тот же приём, что у
`Stats/parts/StatsHeader.tsx` и `Steps/parts/StepsHeader.tsx`);
`grid-links` строит собственный заголовок в две колонки (не вынесен в
`parts/` — раскладка нужна только этому варианту).

| Поле | Обязательное | По умолчанию | Примечание |
|---|---|---|---|
| `items: FeatureItem[]` (`title`, `text`, `icon?`, `points?`, `number?`, `photo?`, `link?`, `tags?`) | да | — | `icon` — ключ из `lib/icons.ts` (`IconName`). `link`/`tags` — опциональные, читают только карточные варианты (см. таблицу ниже) |
| `surface` | нет | `"surface"` | |
| `variant` | нет | `"table"` | см. таблицу вариантов |
| `columns: 2 \| 3` | нет | `2` | читают `table`/`grid-links` |
| `action?` | нет | — | кнопка под сеткой. Читает только `cards-cta` |
| `number`, `eyebrow`, `title`, `lead` | нет | — | обычные |
| — | — | — | если у `item` есть `photo` — рендерится в боксе `aspect-[4/3] overflow-hidden` (`Features/parts/FeatureContent.tsx`), не произвольным `width`/`height` |

**Варианты (`variant`):**

| Значение | Раскладка | `photo` |
|---|---|---|
| `table` | линейки-разделители, без карточек | форсирует `cards` (см. ниже) |
| `cards` | `Card variant="framed"` | ок |
| `cards-cta` | заголовок пилюлей по центру, карточки со ссылкой «Подробнее» (`item.link`), опциональная кнопка (`action`) под сеткой | ок (карточка) |
| `grid-links` | заголовок в две колонки (заголовок слева, лид справа), сетка на линейках, как `table`, но со стрелкой-ссылкой (`item.link`) в углу ячейки | форсирует `cards` |
| `bento` | заголовок пилюлей по центру, первый элемент — на всю ширину с акцентной рамкой (`item.tags` — плашки под его описанием), остальные — обычная сетка в 2 колонки. Асимметрию 2×2 из референса не повторяет — как и в `Stats`/`Bento`, `Steps`/`NumberedCards`, это отдельная задача на произвольные col-span/row-span (см. нишу «Бизнес — SaaS», раздел 6) | ок (карточка) |

**Если у хотя бы одного `item` задан `photo`, а `variant` — `table` или
`grid-links`** (у обоих рамки рисует `grid`, а не карточка, и он не умеет
выравнивать фото произвольной высоты) — роутер форсирует `variant="cards"`,
значение из конфига игнорируется (в dev — `console.warn`), см. раздел 2.

### Steps — `Steps/`, тип `"steps"`

Восемь вариантов. `rail`/`stack`/`numbered-nodes` — исходные, заголовок
берут из обычного `SectionHeader` (колонтитул на левом поле). Пять
новых читают заголовок через свой `parts/StepsHeader.tsx` (эйброу
пилюлей или обычной подписью, заголовок и лид по центру или слева) —
тот же приём, что и у `Stats/parts/StatsHeader.tsx`, компонент свой,
не общий: раскладка шапки завязана на конкретную секцию.

| Поле | Обязательное | По умолчанию | Примечание |
|---|---|---|---|
| `items: StepItem[]` (`number`, `title`, `text`, `meta?`, `icon?`, `photo?`, `featured?`) | да | — | `number` тут — строка шага («01»), не путать с `SectionBase.number`. `icon`/`photo`/`featured` — опциональные, читают только карточные варианты (см. таблицу ниже); `rail`/`stack` тоже читают `icon`, если он задан |
| `surface` | нет | `"paper"` | |
| `variant` | нет | `"rail"` | см. таблицу вариантов |
| `image?` | нет | — | фото для `variant="split"`. Без него эта раскладка не рендерится (роутер в dev — `console.warn`) |
| `number`, `eyebrow`, `title`, `lead` (SectionBase) | нет | — | обычные |
| — | — | — | `numbered-nodes`: `item.number` становится бейджем-нодой на оси (круг `size-10` на линии), шаг — `Card variant="elevated"`; на `md+` карточки чередуют стороны, ось по центру, на мобильном ось слева и все карточки справа от неё. Зазор между шагами — `padding-bottom` внутри `<li>`, а не внешний margin: отрезок оси рисуется абсолютом внутри того же `<li>` и через margin рвался бы. Карточка подсвечивается тенью на hover, но без `hoverEffect` — шаг никуда не ведёт, и `cursor-pointer` обещал бы клик, которого нет |

**Варианты (`variant`):**

| Значение | Раскладка |
|---|---|
| `rail` | 4 колонки на общей линейке; `icon`, если задан — над номером шага |
| `stack` | та же линейка, 2 колонки |
| `numbered-nodes` | вертикальный таймлайн: номера-бейджи на оси, карточки по сторонам |
| `cards` | заголовок пилюлей по центру, ряд карточек: круглая плашка под иконкой, «N. Заголовок» одной строкой, описание |
| `cascade` | карточки каскадом (каждая следующая ниже и правее предыдущей), номер — акцентный бейдж на углу карточки. Тёмный/светлый вид референса — не два компонента, а одни и те же данные на разной поверхности: `surface="ink"` + `photo` у items даёт мрачную версию, обычная поверхность без фото — светлую и лёгкую |
| `timeline` | горизонтальная линия с круглыми нодами-иконками, заголовок и описание под каждой нодой; первая нода — с акцентным кольцом (статичный акцент «с чего начинается», не состояние прогресса — в данных нет понятия «текущий шаг») |
| `split` | фото с заголовком/лидом поверх слева (та же идея, что у `Stats` `variant="photo"`), сетка 2×2 карточек справа с числом-водяным знаком; `item.featured` красит карточку акцентной заливкой (`data-surface="accent"`) |
| `numbered-cards` | ряд карточек: кружок-номер + соединительная линия, иконка, заголовок, описание, фото в подвале; `item.featured` — карточка на `data-surface="ink"` |

### Gallery — `Gallery/`, тип `"gallery"` (кейсы/работы)

Пять вариантов. `register`/`grid` держат `surface="ink"` по умолчанию
(единственный тёмный блок на странице) и заголовок через обычный
`SectionHeader`. Три новых карточных варианта читают заголовок через
свой `parts/GalleryHeader.tsx` (пилюля-эйброу + опциональная кнопка
`action` справа — тот же приём, что у `Stats`/`Steps`/`Features`, но с
кнопкой, а не центрированием) и по умолчанию стоят на `surface="surface"`.

| Поле | Обязательное | По умолчанию | Примечание |
|---|---|---|---|
| `items: CaseItem[]` (`category`, `problem`, `result`, `year`, `status?`, `tags?`, `title?`, `photo?`, `link?`, `icon?`, `date?`, `stats?`) | да | — | `title`/`photo`/`link`/`icon`/`date`/`stats` — опциональные, читают только карточные варианты (см. таблицу ниже) |
| `note?` | нет | — | сноска под реестром (только `register`/`grid`) |
| `surface` | нет | `"ink"` (`register`/`grid`) | карточные варианты по умолчанию `"surface"` |
| `variant` | нет | `"register"` | см. таблицу вариантов |
| `action?` | нет | — | кнопка в шапке секции. Читает только `cards-icon` |
| `status?` (на элементе) | нет | — | колонка-статус, рендерится через `Badge variant="soft"`. **Колонка появляется в шапке и строках, только если `status` задан хотя бы у одного элемента**: без неё раскладка прежняя (3/4/4/1), с ней — 3/3/3/2/1, те же 12 колонок. Четыре блока живут в `components/sections/` по тому же устройству папки,

полей `siteConfig.header.variant` / `siteConfig.footer.variant`
(`HeaderVariant` / `FooterVariant` в `types/site.ts`).

| `Footer/` | `app/page.tsx` | `brand`, `contacts`, `footer`, `nav` (`footer.variant?` — тот же паттерн, что у Stats.containerVariant: поле внутри объекта, а не отдельный проп) | `default`, `bold`, `classic`, `compact`, `gradient`, `centered`, `glass`, `split` |

| `Privacy/` | `app/privacy/page.tsx` | `brand`, `contacts`, `siteUrl` | `Default` |

`NotFound` и `Privacy` пока держат один вариант каждый, и роутер
выглядит избыточным — он там именно ради единообразия: второй дизайн
404 добавляется тем же алгоритмом, что и второй дизайн любой секции
(раздел 7), а не «сначала распилим монолит». Когда появится второй
вариант, ручку нужно завести в `siteConfig` (как уже сделано для

**Варианты Header** (`siteConfig.header.variant`, по умолчанию

  вешает свой TODO именно туда).

## 2. Фото в секциях: обязательное правило

Любая секция, у типа `item` которой в `types/site.ts` есть `photo?`
(`FeatureItem`, `PricingPlan`, `TeamMember`) — обязана рендерить такие
элементы только через `Card variant="framed"` (или эквивалентную
раскладку с независимой высотой ячейки) и фиксированный aspect-ratio
контейнер для картинки (`aspect-[4/3]` / `aspect-square` /
`aspect-[3/4]` — какой подходит конкретной секции, но один и тот же на
всех карточках внутри одной секции, без исключений). Табличный/
бордюрный `variant` (`Features` `"table"`, `Pricing` `"table"`) и фото
в одном компоненте **не смешивать никогда**: рамки в табличном
варианте рисует сетка (`border-top`/`border-l` на ячейке), а не
карточка, и она ничего не знает про высоту фото произвольного
размера — это и есть источник «кривых» сеток при добавлении фото в
конфиг без доработки компонента.

Практическое следствие: `Features` и `Pricing` **сами** форсируют
`variant="cards"`, если хотя бы у одного элемента массива задан
`photo`, независимо от того, что указано в `site.config.ts` (с
`console.warn` в dev-режиме) — специально, чтобы на это нельзя было
случайно не полагаться в конфиге: если человек, не знающий про это
правило, добавит `photo` в `variant="table"`, компонент сам уходит в
`"cards"`, а не молча ломает сетку. У `Team` нет отдельного табличного
варианта, но по той же логике фото и заглушка-инициалы делят один и
тот же бокс фиксированного размера (`aspect-[3/4]`), а не два разных
места разной высоты.

При добавлении нового типа секции с `photo?` на элементах массива —
это правило обязательное, а не best practice: без форсирования
`variant` и без aspect-ratio контейнера сетка при смешанных данных
(часть элементов с фото, часть без) поплывёт так же, как плыла в
`Features`/`Pricing` до этой правки.

### Источник картинок: только локальные файлы в `public/images/`

Все значения `photo?` (`FeatureItem`, `PricingPlan`, `TeamMember`),
`AboutSection.photo` и `HeroSection.image` — обязаны быть локальным
путём вида `/images/имя-файла.jpg`, то есть указывать на файл,
реально лежащий в `public/images/` в этом проекте. Внешний URL
(`https://images.unsplash.com/...` и подобные) подставлять в эти поля
**нельзя**.

Причина не стилистическая, а рантайм-ошибка: `next.config.ts` в
шаблоне не задаёт `images.remotePatterns`, а `next/image` по
умолчанию отклоняет любой внешний хост, которого нет в этом списке —
такая картинка не просто не оптимизируется, а падает с ошибкой прямо
в браузере (`Invalid src prop... hostname is not configured`),
причём только в момент рендера конкретной секции, а не на сборке, так
что дефект легко пропустить, если тестировали только с локальными
фото. Это осознанный выбор шаблона: **только локальные фото**, а не
`images.remotePatterns` — расширять список разрешённых внешних хостов
под конкретные источники (например `images.unsplash.com`) в этом
шаблоне не нужно и не предполагается.

Практическое следствие: перед тем как прописать `photo`/`image` в
`site.config.ts`, файл сначала нужно скачать и положить в
`public/images/` этого проекта (см. `coffee-shop/public/images/` —
там `hero.jpg`, `about.jpg`, `menu-latte.jpg`, `menu-croissant.jpg`
уже лежат локально именно по этой причине, а не оптимизации ради).

## 3. Как SectionRenderer сопоставляет `site.config.ts` с компонентами

`components/SectionRenderer.tsx` — реестр вида
`{ [K in SectionType]: Renderer<K> }`: обычный объект, ключ — строковый
литерал `type` секции (`"hero"`, `"stats"`, …), значение — функция вида
`(section, context) => ReactNode`.

Рендер (`SectionRenderer` компонент) проходит `sections` из
`site.config.ts` через `.map`, для каждого элемента берёт
`registry[section.type]` и вызывает с `(section, context)`, где
`context` = `{ contacts }` — это то самое место, откуда `ContactForm`
получает `contacts`, не будучи частью объекта секции в конфиге.

Типобезопасность обеспечивает `Extract<Section, { type: K }>` —
TypeScript проверяет, что пропсы, которые дойдут до конкретного
компонента (`<Hero {...section} />` и т.п.), соответствуют интерфейсу
именно этого типа секции, а не union целиком.

Если в `sections` встретился `type`, которого нет в `registry` (опечатка
или недобавленный тип) — `SectionRenderer` не падает, а в dev-режиме
пишет `console.warn` и рендерит `null` для этого элемента
(`SectionRenderer.tsx:75-81`). В проде — тихо `null`, без предупреждения.

## 4. Подход к неиспользуемым секциям: обычный `import`, вручную

Сейчас в файле — **статические импорты**, не `next/dynamic`. Это
осознанный откат, а не «ещё не сделали»: `next/dynamic` тут пробовали и
отказались, потому что он не решает задачу — см. ниже, почему.

### Почему не next/dynamic

`registry[section.type]` — это выбор компонента **по строке из данных**
(`site.config.ts`), а не по литеральному условию в коде. Бандлер
(что Turbopack, что Webpack — проверено оба) решает, что попадёт в
собранный JS, по статическому анализу самого кода, а не по содержимому
другого файла: он не умеет доказать, что конкретный `type` никогда не
встретится в `sections`, и поэтому не может выкинуть код
соответствующего компонента.

Экспериментально: если обернуть каждый компонент в
`dynamic(() => import(...))` и убрать секцию `faq`/`contact` из
`site.config.ts`, JS `Accordion` и `ContactForm` (`Toast`, `Select`)
всё равно оказывается в собранном бандле страницы — байт в байт как при
включённой секции. `next/dynamic` в этой схеме не даёт вообще никакого
выигрыша, а только усложняет код (лишний уровень React.lazy/Suspense).
Поэтому реестр вернули к обычным `import`.

Отдельно: у большинства секций (`Hero`, `Stats`, `Features`, `Steps`,
`Gallery`, `Testimonials`, `Team`, `About`, `Pricing`, `CTA`) вообще нет
собственного клиентского JS — это чистые Server Components без `"use
client"` где-либо в дереве, их код и так не попадает в бандл браузера
независимо от способа импорта. Реальный клиентский вес есть только у
двух секций: `FAQ` (через `Accordion`) и `ContactForm` (форма, `Toast`,
`Select`) — и если секция реально есть на странице, этот вес неизбежен
в любом случае.

### Если в проекте секция реально не нужна — как убрать её JS вручную

Единственный способ, который реально работает: руками убрать секцию из
самого `SectionRenderer.tsx` в этом конкретном проекте (шаблон
клонируется на проект, и правка одного файла — это ожидаемая, разовая
операция, а не то, что должно происходить автоматически).

Пример — в проекте нет ни FAQ, ни формы обратной связи:

1. Удалить импорт `import { FAQ } from "@/components/sections/FAQ";`
   и `import { ContactForm } from "@/components/sections/ContactForm";`
   из шапки файла.
2. Удалить соответствующие строки из объекта `registry`:
   `faq: (section) => <FAQ {...section} />,` и
   `contact: (section, context) => (<ContactForm ... />),`.
3. Убрать `FaqSection`/`ContactSection` из union `Section` в
   `types/site.ts` (и сами интерфейсы, если не нужны). **Это обязательный
   шаг, а не опциональный**: `registry` типизирован как
   `{ [K in SectionType]: Renderer<K> }` — это маппированный тип, где
   каждый ключ `SectionType` обязателен, без `?`. Если после шага 2
   `"faq"`/`"contact"` всё ещё остаются в `SectionType`, TypeScript
   даст ошибку `Property 'faq' is missing in type ...` прямо на
   объявлении `registry` (проверено: `tsc` действительно падает на
   таком коде, см. `TS2741`). Убрать `"faq"`/`"contact"` из
   `SectionType` без правки самого union `Section` нельзя — `SectionType`
   выводится из него (`Section["type"]`).
4. Альтернатива, если не хочется трогать `types/site.ts`: сменить
   тип `registry` с `{ [K in SectionType]: Renderer<K> }` на
   `Partial<{ [K in SectionType]: Renderer<K> }>`. Тогда шаг 3 не
   нужен — недостающие ключи (`faq`, `contact`) просто не потребуются,
   а существующая ветка `if (!render) { ...warn...; return null; }`
   в `SectionRenderer` (`SectionRenderer.tsx:75-81`) уже готова к этому
   случаю. Минус: если кто-то по ошибке добавит `type: "faq"` обратно в
   `site.config.ts`, TypeScript это пропустит (тип `Section` всё ещё
   разрешает такой объект), и секция молча не отрендерится — заметно
   только по `console.warn` в dev. Шаг 3 (сузить union) строже: такая
   ошибка не скомпилируется вообще.
5. Убедиться, что в `content/site.config.ts` нет объектов с
   `type: "faq"` / `type: "contact"` — при шаге 3 без этого будет ошибка
   типов на самом объекте секции в конфиге.
6. Пересобрать (`npm run build`) и проверить, что `Accordion`/`Toast`/
   `Select` больше не встречаются в `.next/static/chunks/*.js`
   (`grep -rl "Accordion" .next/static/chunks/`).

### Чтобы добавить новую секцию (не убрать, а добавить)

1. Тип и интерфейс в `types/site.ts`, добавить в union `Section`.
2. Папка секции в `components/sections/<Название>/` — по тому же
   шаблону, что и все остальные: `index.tsx` (роутер) +
   `variants/<Вариант>.tsx`. Подробно — раздел 7.
3. Обычный `import` сверху `SectionRenderer.tsx` + строка в `registry`.
   Импортируется папка (`@/components/sections/<Название>`), файл
   разрешается в `index.tsx`.
4. Если у секции есть `variant` — добавить её в таблицу дефолтов
   `lib/preset.ts` (какая раскладка берётся в каком тарифе) и в
   резолвинг в `registry`.
5. Объект в `sections` внутри `content/site.config.ts`.

Больше нигде ничего подключать не нужно (это же в `README.md`, раздел
«Добавить новую секцию» — здесь то же самое, но с объяснением, почему
шаг 3 — это именно обычный `import`, а не `next/dynamic`).

## 5. Примитивы: `Card`, `Badge` и слой глубины

Это то, чем тарифы отличаются друг от друга технически. Механику секций
они не трогают: в `SectionRenderer` и `site.config.ts` ничего для них
подключать не нужно. Полная картина по тарифам — `docs/presets.md`.

### `components/ui/Card.tsx`

Ни одного значения тени, радиуса и цвета в компоненте нет: варианты —
это набор классов слоя глубины, а сами значения приходят из токенов
`--card-*` / `--radius-card` (`theme/tokens.css`) и зависят от тарифа.

| `variant` | Классы | Когда |
|---|---|---|
| `cell` (по умолчанию) | только паддинги | ячейка табличной сетки: границы рисует родитель |
| `framed` | `ui-card border` | **карточка по умолчанию**: в «Экономе» hairline-рамка на фоне своей секции без тени, в «Стандарте» — собственная поверхность + тень + радиус 16px, в Premium — приглушённая акцентная рамка. Именно её ставят все секции; выбирать глубину руками не нужно |
| `elevated` | `ui-card ui-card--elevated border` | явно поднятая карточка **независимо от тарифа**: собственная поверхность + тень. Для мест, где подъём нужен по смыслу, а не по тарифу — виджет hero, форма в `layout="cardContainer"`, шаг таймлайна |
| `bordered-accent` | `ui-card ui-card--accent border` | та же поверхность, но глубина рамкой, а не тенью (тень принудительно `none` в любом тарифе) |
| `plain` | ничего, даже паддингов | контент сам знает, как себя оформить |

`hoverEffect?: boolean` (по умолчанию `false`) добавляет
`ui-card--interactive cursor-pointer` — это подменяет
`--card-shadow-hover` / `--card-lift` на «интерактивные» значения
(`--card-hover-shadow` / `--card-hover-lift`). В «Экономе» это ровно
прежнее поведение (`shadow-card-hover` + подъём на 4px), в «Стандарте»
— более сильный подъём поверх и без того живой карточки. Сдвиг всегда
под `prefers-reduced-motion: no-preference`, тень меняется плавно
в любом случае. **`cursor-pointer` входит в набор**, поэтому включать
`hoverEffect` только там, где карточка действительно кликабельна.
Для «живого, но не кликабельного» блока в «Стандарте» ничего включать
не нужно — реакция на курсор там есть у любой карточки; в «Экономе» её
нет и не должно быть.

`framed` теперь не привязан к `bg-bg`: цвет фона приходит из
`--card-bg`, который в базе равен фону своей секции (то есть Эконом
рендерится как раньше), а в дорогих тарифах — `--surface-card`.
Именно этот один токен раньше и делал «Стандарт» плоским: белая
карточка на белой секции с невидимой тенью.

### Классы слоя глубины (`app/globals.css`, `@layer components`)

Компоненты вешают роль, а чем эта роль окажется — решают токены тарифа.
В `components/` не должно быть ни `shadow-*`, ни `rounded-xl`, ни
`hover:-translate-y-*`.

| Класс | Роль | Где применён |
|---|---|---|
| `ui-card` (+ `--elevated` / `--accent` / `--featured` / `--live` / `--interactive`) | карточка. `--live` — реагирует на курсор тенью, но без `cursor-pointer` (карточка никуда не ведёт); `--interactive` — то же, что `hoverEffect` | `Card`, контейнер `Stats`, таймлайн `Steps` |
| `ui-button` | радиус, тень покоя и подъём кнопки | `Button` |
| `ui-control` | геометрия поля: подчёркивание (Эконом) или коробка (Стандарт) | `Input`, `Select` |
| `ui-media` | скругление медиа **внутри** карточки (без тени — она дала бы двойной ореол) | фото `Features` / `Pricing`, аватар `Team` |
| `ui-media-raised` | скругление + тень самостоятельного медиа | фото `Hero` и `About`, карта в контактах |
| `ui-popover` | радиус и тень всплывающей панели | `Toast`, меню `Select` |
| `ui-accordion`, `ui-accordion-item` | список на линейках (Эконом) или стопка карточек (Стандарт) | `Accordion` |
| `ui-header` | фон, blur и тень хедера | `Header` |
| `icon-tile` | плашка под иконкой: в Экономе нулевой паддинг и прозрачный фон, то есть голая иконка на прежнем месте | `Features` |
| `[data-section]`, `[data-tint="hero"]` | фоновая подсветка секции | `Section` (`tint="hero"` ставит один `Hero`) |

Они лежат в `@layer components`, а не в utilities и не вне слоёв —
специально: обычные утилиты Tailwind (`border-fg` у выделенного тарифа,
`h-full`, `mt-*`) должны их перебивать, а слой utilities идёт после
components.

### `components/ui/Badge.tsx`

| `variant` | Классы | Когда |
|---|---|---|
| `soft` (по умолчанию) | `bg-badge-soft text-badge-soft-fg` | статусы в реестре, бейдж виджета в hero |
| `outline` | `border border-rule font-mono uppercase text-fg-muted` | теги, коды — где важна не эмоция, а различимость |

Кегль у обоих — `text-caption` (13px + трекинг капса) из общей шкалы, а
не произвольные 12px: размеров шрифта вне токенов в шаблоне нет.

Пара цветов у `soft` — не `bg-accent/10 text-accent` напрямую, а
`--badge-soft-bg` / `--badge-soft-fg`, и это принципиально: реестр
кейсов живёт на `surface="ink"`, где хвойный акцент на графите не
читается вообще. Пара переопределена в `[data-surface="ink"]` (светлый
текст блока на 12%-подложке) и в `[data-surface="accent"]`; компонент
про это не знает.

### Токены глубины и радиусов (`theme/tokens.css` → `@theme inline`)

Значения в колонке — это база, то есть тариф «Эконом». Что из этого
переопределяет «Стандарт» — таблица в `docs/presets.md`, раздел 2.1.

| Токен в `tokens.css` | Утилита | Значение (светлая тема, Эконом) |
|---|---|---|
| `--elevation-none` | `shadow-none` | `none` |
| `--elevation-sm` | `shadow-sm` | `0 1px 2px 0 rgb(0 0 0 / 0.05)` |
| `--elevation-md` | `shadow-md` | `0 4px 20px -2px rgb(0 0 0 / 0.06)` |
| `--elevation-lg` | `shadow-lg` | `0 10px 30px -4px rgb(0 0 0 / 0.08)` |
| `--elevation-card-hover` | `shadow-card-hover` | `0 12px 32px -4px rgb(0 0 0 / 0.12)` |
| `--radius-sm` / `--radius-md` | `rounded-doc-sm` / `rounded-doc` | 2px / 4px |
| `--radius-lg` / `--radius-xl` / `--radius-2xl` | `rounded-lg` / `rounded-xl` / `rounded-2xl` | 12px / 16px / 24px |
| `--radius-card` | `rounded-card` | `var(--radius-md)` — роль «карточка», ступень выбирает тариф |
| `--radius-control` | `rounded-control` | `var(--radius-sm)` — роль «кнопка и поле» |
| `--radius-pill` | `rounded-pill` | `var(--radius-sm)` — роль «бейдж, полоса прогресса» |
| `--radius-media` | (через `.ui-media*`) | `var(--radius-sm)` — роль «фото, карта, аватар» |
| `--card-bg` / `--card-border` / `--card-shadow` / `--card-lift` | (через `.ui-card`) | фон своей секции / hairline / `none` / `0` |
| `--btn-shadow` / `--btn-lift` | (через `.ui-button`) | `none` / `0` |
| `--icon-tile-padding` / `--icon-tile-bg` | (через `.icon-tile`) | `0` / `transparent` |
| `--section-tint` / `--hero-tint` | (через `[data-section]`) | `none` |
| `--control-*`, `--accordion-*`, `--popover-*`, `--header-*` | (через одноимённые классы) | значения базы: подчёркивание, линейки, 4px, без тени |
| `--surface-card` | `bg-card` | цвет своей секции (см. ниже) |
| `--accent-border` | `border-accent-border` | `var(--accent)` |
| `--badge-soft-bg` / `--badge-soft-fg` | `bg-badge-soft` / `text-badge-soft-fg` | акцент на 10%-подложке |
| `--font-mono-stack` | `font-mono` | системный моношрифт |

Пять вещей, которые стоит знать про этот слой:

0. **Токены, значение которых зависит от поверхности, обязаны
   объявляться внутри `[data-surface]`, а не в `:root`.** `var()`
   внутри custom property подставляется в момент вычисления на том
   элементе, где объявлен, — то есть `--card-bg: var(--surface-bg)` в
   `:root` посчитается один раз по `paper` и дальше будет просто
   наследоваться, игнорируя тёмный блок. Поэтому в `tokens.css` есть
   отдельное правило на селекторе `[data-surface]` (без значения — одно
   на все четыре поверхности), где такие токены пересчитываются на
   каждой секции. Та же причина, по которой там же живёт
   `--surface-card`.

1. **`--radius-sm`/`--radius-md` намеренно остались 2/4px**, хотя
   расширенная шкала обычно начинается с 4/8px. На этих двух значениях
   свёрстана вся текущая база (`rounded-doc*`), и их сдвиг переверстал
   бы Эконом. Шкала поэтому растёт вверх, а компоненты выбирают не
   ступень, а **роль** (`--radius-card` / `--radius-control` /
   `--radius-media` / `--radius-pill`) — какую ступень означает роль,
   решает тариф. Компоненты про конкретные px не знают.
2. **Имена в `tokens.css` — `--elevation-*`, а не `--shadow-*`**: в
   утилиты они приезжают через `@theme inline` в `app/globals.css`, и
   одноимённая переменная там дала бы самоссылку. По той же причине
   `--radius-lg: var(--radius-lg)` в `@theme inline` — не опечатка:
   при `inline` переменная не эмитится в `:root`, а подставляется в
   утилиту как есть, а значение приходит из `tokens.css`.
3. **В тёмной теме `--elevation-*` усилены** (альфа 0.4–0.6 вместо
   0.05–0.12): чёрный с альфой 0.05 по тёмной бумаге не даёт вообще
   никакой разницы. Форма и радиусы теней те же.
4. **`--surface-card` объявляется заново в каждом `[data-surface]`**, а
   не один раз в `:root`: `var(--surface-bg)` внутри `:root`
   посчитался бы один раз по paper и дальше только наследовался. На
   `paper`/`surface` это белый лист, на `ink` — тон на несколько
   процентов светлее фона блока (на тёмном тень не работает как
   подъём), на `accent` — подмешанный `--accent-fg`.

Дубли значений лежат в `theme/palette.ts` (`elevation`, `radius`) — там
же, где и палитра, и по той же причине: рантайм без CSS (og-картинка,
письма из `/api/contact`). В компонентах эти объекты не используются.

## 6. Тарифы и ниши

Тарифы (`econom` / `standard` / `premium`) описаны отдельно и подробно —
**`docs/presets.md`**. Там же чек-лист сборки «Стандарта», разбор того,
почему он раньше выходил плоским, и готовый пример конфига. Здесь —
только то, что касается ниш поверх тарифа.

Короткое напоминание, чтобы не читать два документа:

```ts
// content/site.config.ts — весь тариф целиком
theme: { /* ... */ preset: "standard" },
```

Это переключает и пластику (тени, радиусы, поверхности карточек,
подсветку секций, плашки под иконками, стеклянный хедер, поля-коробки),
и дефолтные `variant` секций на карточные. Ни `tokens.css`, ни
компоненты руками править **не нужно**.

Компонентная система (типы секций, `SectionRenderer`, `Section` /
`Container` / `Card` / `SectionHeader`) — общая для всех проектов и для
всех тарифов. Разница между **нишами** делается не новыми компонентами,
а палитрой (`--palette-*` в `theme/tokens.css` + `theme/palette.ts`),
шрифтами и составом секций.

Текущая база (юрбюро) — сознательно строгая: один акцент
(`--palette-accent: #14452f`) в шести местах, документный радиус 4px,
ни одной тени на странице, серия serif (Source Serif 4 / Playfair) +
Golos Text, `preset: "econom"`.

Ниже — три ниши как примеры того, что меняется **сверх** выбора тарифа.

### Эконом — кофейня

Тариф: `preset: "econom"`. Минимальные изменения от базы: серьёзность
юрбюро и так близка к «опрятно и по делу», нужно только снять строгость
и добавить тепла.

- **Акцент**: тёплый, не хвойный — например обжаренный терракот/карамель
  (`--palette-accent: #a8582f` или похожий, подобрать под конкретный
  бренд) вместо холодного `#14452f`. Правило «6 мест» — оставить как
  есть, оно не про юристов конкретно, а про дисциплину акцента вообще.
- **Радиус**: если хочется мягче, поднять не `--radius-md` (он
  документный, на нём висит вся база), а роль `--radius-card` — до
  `--radius-lg` (12px): карточки меню читаются менее «документом»,
  более «меню кафе», а пластика кнопок и полей не меняется (у них своя
  роль — `--radius-control`). Это единственная уместная точечная правка
  токена в Экономе; всё остальное лучше делать сменой тарифа.
- **Тени**: не добавлять — Эконом плоский по определению. Если нужна
  глубина, это не «включить тени в Экономе», а `preset: "standard"`.
- **Шрифты**: можно оставить serif-заголовки как есть (Source
  Serif 4 хорошо читается и для «крафтового» позиционирования), либо
  заменить `--font-heading-stack` на что-то более круглое/дружелюбное —
  решается под конкретный бренд, не автоматически.
- **Секции**: `hero` (`type-only`), `features` → `variant: "cards"`
  вместо `"table"` (позиции меню как карточки, а не таблица услуг),
  `gallery` можно не использовать вовсе (кейсов у кофейни нет) или
  переиспользовать под «наши локации», `testimonials` → `"quotes"`,
  `pricing` не нужен (меню — это `features`, не тарифы), `contact` →
  оставить, но сократить `fields` до минимума (имя + телефон).

### Стандарт — курс, товар (клавиатура)

Тариф: `preset: "standard"`. Пластику (радиусы, тени, поверхности
карточек, плашки под иконками, скруглённые кнопки и поля) он даёт сам —
руками ничего из этого настраивать не нужно и не следует.

- **Акцент**: один яркий цвет под бренд продукта (не хвойный и не
  строго-синий) — например индиго/фиолетовый или тёплый оранжевый,
  в зависимости от продукта. Правило «6 мест» в этом тарифе уже
  ослаблено самим пресетом ровно в двух местах: плашка под иконкой
  (`--icon-tile-bg`/`--icon-tile-fg`) и рамка выделенного тарифа
  (`--card-featured-border`). Дальше ослаблять — только явно и
  осознанно.
- **Секции**: `variant` лучше не указывать вовсе — дефолты тарифа уже
  карточные (см. таблицу в `docs/presets.md`). Указывать имеет смысл
  только осознанное отступление. Что стоит добавить по содержанию:
  `hero` → `image` с фото товара **или** `widget` с метриками курса
  (без одного из них `split` откатится на `type-only`); `features` →
  `icon` каждому элементу (в этом тарифе у иконки плашка, без неё
  карточка пустовата); `gallery` → примеры работ выпускников со
  `status`/`tags`; `pricing` → `featured: true` на рекомендуемом тарифе
  (получит акцентную рамку и усиленную тень); `contact` → форма
  записи/предзаказа.
- **`hoverEffect`** — только если карточка реально ведёт на страницу
  товара/урока: в наборе `cursor-pointer`. Живой отклик на курсор в
  этом тарифе есть у любой карточки и без него.

### Бизнес — SaaS («Смена», референс Aeterna)

Референс: синий акцент, скругления, bento-сетка, SaaS-тарифы. Это самый
дальний отход от базы, и часть требований **не покрыта существующими
компонентами** — ниже явно отмечено, что можно сделать токенами, а что
требует нового кода.

Тариф: `preset: "standard"` (или `"premium"`, если референс без теней).

- **Акцент**: синий (`--palette-accent: #2563eb` или похожий,
  подобрать под конкретный бренд), `--accent-fg` пересчитать под
  контраст с синим фоном заливки (сейчас `--accent-fg` — это
  `--palette-paper`, тёплый оффвайт; для синего SaaS обычно нужен
  чистый белый). Правило «6 мест» для SaaS обычно и так ослаблено
  рынком (акцент на бейджах фич, ссылках, активных табах) — если решаем
  ослаблять сверх того, что уже делает пресет, прописать явно в
  README проекта, а не молча.
- **Радиус и пластика**: закрыто тарифом целиком. `--radius-card` (16px),
  `--radius-control` (12px — кнопки и поля, теперь у них своя роль, а не
  документные 2px), `--radius-media`, `--radius-pill` — всё
  переключается пресетом. Отдельной правки `Button.tsx`/`Input.tsx`
  больше не требуется.
- **Тени**: закрыто тарифом. `--elevation-*` в «Стандарте» —
  двухслойные и реально видимые; тень есть у карточек, кнопок, хедера,
  тоста, меню селекта и самостоятельных фото.
- **Bento-сетка**: в проекте **не реализована** ни в каком виде —
  `Card` умеет только `cell`/`framed`/`plain` с одинаковым размером
  ячеек внутри обычной CSS-grid, разных spans (широкая карточка + две
  узкие рядом, как в типичном bento) сейчас нет ни у `Features`, ни у
  `Pricing`, ни у отдельного компонента. Для этого пресета это
  отдельная задача: либо новый `variant="bento"` у `Features` с
  ручными `col-span`/`row-span` на части `items`, либо новый компонент
  секции (`BentoGrid`) — в любом случае это выходит за рамки «поменять
  токены и variant», нужна доработка `components/sections/Features/`
  или новый файл.
- **SaaS-тарифы**: `pricing` секция уже покрывает большую часть —
  `variant: "cards"`, `featured` на плане, `unit` (например «/ мес»),
  `action` (кнопка на план). Не хватает по сравнению с типичным
  SaaS-референсом: переключателя «месяц/год» (в `PricingSection` такого
  поля нет вообще, `types/site.ts` его не описывает) — это тоже
  доработка типа `PricingSection` + компонента, а не просто новый
  вариант конфига.
- **Секции**: `variant` в тарифе `standard` подставляется сам и уже
  соответствует SaaS-референсу (`hero: split`, `features: cards`,
  `stats: grid + elevated`, `pricing: cards`, `contact: cardContainer`).
  По содержанию добавить: `hero.image` со скриншотом продукта **либо**
  `hero.widget` с метриками (ровно тот SaaS-паттерн, что в референсе),
  короткую форму в `contact` (обычно email + опционально компания), а не
  полный набор полей как у юрбюро.

## 7. Как добавить новый вариант дизайна

Всё в `components/sections/` устроено ОДИНАКОВО, без исключений — и
секции из конфига, и четыре блока вне его (`Header`, `Footer`,
`NotFound`, `Privacy`, см. конец раздела 1), включая те, у кого вариант
пока один. Смысл в том, что новый дизайн всегда добавляется одним и тем
же алгоритмом, и не надо каждый раз сначала распиливать монолит.

### Структура папки секции

```
components/sections/<Название>/
  index.tsx            — роутер: по props.variant выбирает файл из variants/
  variants/<V>.tsx      — законченный вариант: рендерит секцию ЦЕЛИКОМ
  parts/*.tsx           — куски разметки, общие для нескольких вариантов
  types.ts              — только если пропсы шире типа секции: у ContactForm
                          (секция + contacts) и у всех четырёх блоков вне
                          конфига (Header, Footer, NotFound, Privacy — у них
                          своего типа в types/site.ts нет вообще)
```

Точка импорта не меняется: `SectionRenderer.tsx` по-прежнему пишет
`import { Hero } from "@/components/sections/Hero"` — путь резолвится
в `index.tsx` папки.

### Три шага

**1. Создать файл в `variants/`.** Проще всего скопировать соседний
вариант и переписать разметку. Вариант принимает пропсы своей секции
целиком (тот же тип, что в `types/site.ts`) и рендерит всю секцию — от
`<Section>` до закрывающего тега:

```tsx
// components/sections/Features/variants/Bento.tsx
import { Container } from "@/components/ui/Container";
import { Section } from "@/components/ui/Section";
import { SectionHeader } from "@/components/ui/SectionHeader";
import { FeatureContent } from "../parts/FeatureContent";
import type { FeaturesSection } from "@/types/site";

export function Bento(props: FeaturesSection) {
  const { id, surface = "surface", number, eyebrow, title, lead, items } = props;

  return (
    <Section id={id} surface={surface}>
      <Container>
        <SectionHeader number={number} eyebrow={eyebrow} title={title} lead={lead} />
        {/* ...своя раскладка... */}
      </Container>
    </Section>
  );
}

export default Bento;
```

**2. Добавить значение в тип секции** (`types/site.ts`):

```ts
export interface FeaturesSection extends SectionBase {
  type: "features";
  variant?: "table" | "cards" | "bento";   // ← новое значение
  ...
}
```

**3. Добавить строку в `index.tsx` этой секции:**

```tsx
import { Bento } from "./variants/Bento";

const variants: VariantMap<FeaturesSection, NonNullable<FeaturesSection["variant"]>> = {
  table: Table,
  cards: Cards,
  bento: Bento,   // ← новая строка
};
```

Порядок шагов важен: `VariantMap` — это `Record<V, …>`, где `V` — весь
union `variant`. Добавили значение в тип (шаг 2), но забыли строку в
роутере (шаг 3) — TypeScript не соберётся с ошибкой «Property 'bento' is
missing». Забытый вариант не отрендерится пустотой, а сломает сборку —
так и задумано.

### Что писать в вариант, а что в parts/

- **В вариант** — всё, что отличает этот дизайн: сетка, оболочка
  элемента (ячейка / карточка / строка реестра), вертикальный ритм
  секции, поверхность по умолчанию.
- **В `parts/`** — то, что повторяется между вариантами дословно:
  содержимое карточки (`FeatureContent`, `PlanContent`, `MemberContent`),
  оболочка секции, если она общая (`GalleryShell`), клиентская логика
  (`ContactForm/parts/useContactForm.ts`).

Правило простое: скопировали блок разметки во второй вариант без
изменений — значит ему место в `parts/`.

### Два правила карточного варианта

Это не стилистика, а то, на чём карточные раскладки «Стандарта»
ломались раньше. Оба следуют из одного факта: **карточки в ряду имеют
одну высоту (её задаёт самая высокая), а их содержимое — разную.**

**1. Низ карточки прижимается `mt-auto`, а не `mt-*`.** Карточка ставится
как `flex h-full flex-col`, внутренняя обёртка — `flex flex-1 flex-col`,
а последний смысловой элемент (подпись автора, кнопка тарифа, строка
стажа, плашки статуса) получает `mt-auto pt-*`. Без этого подписи в ряду
висят на разной высоте и нижний край читается рваным. `pt-*` вместо
`mt-*` тут обязателен: те же `parts/` переиспользуют табличные
раскладки, где flex-колонки нет и `margin-top: auto` по спецификации
равен нулю — отступ должен держать паддинг.

Так сделано в `Testimonials/variants/Cards`, `Pricing` (кнопка в
`parts/PlanContent`), `Team` (стаж в `parts/MemberContent`),
`Gallery/variants/Grid` (плашки), `Features/variants/Cards`.

Бокс медиа с фиксированным `aspect-ratio` внутри такой колонки обязан
быть `shrink-0` — иначе в высоком ряду flex подминает ему высоту и фото
перестают быть одного формата.

**2. Ступень кегля передаёт вариант, а не `parts/`.** Крупные ступени
(`text-stat` — до 60px, `text-quote` — до 28px) рассчитаны на широкую
колонку. В карточке на 1/3 ширины (~300px содержимого) цена ломается на
две строки, а отзыв превращается в десять строк текста. Поэтому у
`TestimonialBody` и `PlanContent` базового размера НЕТ: `quoteClassName`
/ `priceClassName` — обязательные, и каждый вариант передаёт свою
ступень (`quotes` → `text-quote`, `cards` → `text-lead`; `table` →
`text-stat`, `cards` → `text-h2`).

Причина, по которой это именно проп, а не «база плюс переопределение»:
две утилиты `font-size` в одном `className` конфликтуют по порядку в
СОБРАННОМ CSS, а не по порядку в строке класса — то есть результат
такого переопределения непредсказуем.

Отдельно: цена оборачивается в `whitespace-nowrap`. Строка
«от 90 000 ₽ / инстанция» длиннее колонки, и браузер переносил её по
последнему влезающему пробелу — внутри числа, оставляя «₽» на второй
строке. Переноситься должна единица измерения.

### Шапка раздела в узкой колонке

`SectionHeader` по умолчанию кладёт номер с колонтитулом на левое поле
(3 колонки из 12). В `Container width="narrow"` (760px) это ~170px, и
колонтитул вроде «Вопросы и ответы» рвётся на три строки. Для таких
случаев есть `layout="stacked"` — номер и колонтитул строкой над
заголовком, заголовок во всю ширину. `FAQ/parts/FaqBody` выбирает
раскладку по своей ширине автоматически; новым секциям в узком
контейнере нужно делать так же.

### Чего в варианте быть не должно

Ни `shadow-*`, ни `rounded-xl`, ни `hover:-translate-y-*`, ни hex-цветов.
Глубина и пластика приходят из тарифа — классы `ui-card`, `ui-button`,
`ui-media`, `icon-tile` и роли-радиусы `rounded-card` / `rounded-control` /
`rounded-pill` (см. раздел 5 и `docs/presets.md`). Вариант отвечает за
РАСКЛАДКУ, тариф — за ГЛУБИНУ. Захардкодив тень в варианте, вы ломаете
оба тарифа сразу.

Карточку в новом варианте ставьте через `Card variant="framed"` — это
«карточка по умолчанию», её глубину выберет тариф. `elevated` — только
там, где подъём нужен по смыслу независимо от тарифа.

### Дефолт варианта по тарифу

Если новый вариант должен становиться умолчанием в каком-то тарифе —
это отдельная правка в `lib/preset.ts` (таблица `PRESET_DEFAULTS`), а не
в самой секции. Роутер читает `props.variant`, а подставляет его
`SectionRenderer` — см. `docs/presets.md`, раздел 2.2.

### Вторая ось

У двух секций есть второй, независимый от `variant` переключатель:
`Stats.containerVariant` (подложка под цифрами) и `ContactForm.layout`
(подложка под формой). Такие оси НЕ попадают в `variants/` — иначе
пришлось бы заводить файл на каждую комбинацию (band+flat, band+elevated,
grid+flat…). Они живут в `parts/` общим хелпером, который вызывают все
варианты: `Stats/parts/container.ts`, `ContactForm/parts/FormColumn.tsx`.
Если у новой секции появляется вторая ось — делайте так же.
